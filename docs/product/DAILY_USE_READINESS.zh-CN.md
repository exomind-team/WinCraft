# WinCraft 距离日常使用还有多远

核对日期：2026-11-01。源码基线：`43b804b`。这是现况调查与建议执行顺序，不是新增功能已完成的声明。[English](DAILY_USE_READINESS.en-US.md)。

## 判断

WinCraft 已经能够在真实 Windows 桌面承载有数据、有动作回执的悬浮窗，适合有协助的个人试用。普通用户独立日用的主要缺口是：把安装、选择应用、启动、阅读、临时收起、故障恢复和次日重建连成一条可靠路径。

现有任务账本覆盖内核、契约、示例、原生验收和远期应用。不同层级的 PASS 不能相加成为“产品完成率”；手机、语音或全平台目标未完成，也不必阻止有限 Windows 日用版本。

## 用户希望过怎样的一天

早上打开 WinCraft，从“我的应用”选择 Agent 总览、监控或额度面板。首次导入时查看代码包来源、版本、入口及所需环境；每次执行代码仍由用户明确确认。以后从已安装列表进入，连接参数由宿主交给所选提供者。

工作时只显示必要摘要：值得注意的会话、网络读数、额度和数据时间。要看更多就进入来源页或详情；要继续工作就折叠或隐藏，随后还能找回。字号和不透明度能通过统一入口调整。

关闭源应用后，窗口应诚实显示离线历史；停止采集后，旧数字应显示其年龄。重启 WinCraft 时重新创建世界、握手和租约，用户只需重新确认启动所选应用，不必重新找脚本、复制连接路径、辨认旧进程。

以上是建议的日用验收叙事，部分步骤尚未实现。

## 主要差距与最小修订

### 1. 应用入口仍是开发者入口

双击脚本比手输命令方便，但仍需要找到文件、认识连接描述文件和处理 Python 依赖。`.wcp` 代码包已有预览、仅解包安装、最终确认启动路径；真正可用的应用包、依赖诊断、已安装列表与停止/重新启动入口尚未形成完整体验。

当前 Manager 只在内存中持有本次选中/安装的包。磁盘 Provider store 不等于已完成可恢复的应用库。Launcher 丢弃 stdout/stderr，因此“进程创建成功”之后的缺依赖/立即退出也缺少面向用户的诊断。

Agent 总览当前还带有示例时限：默认 600 秒，允许参数上限 3,600 秒，结束时清理自己的世界。它尚不是常驻应用；不能把运行一会儿后窗口消失归咎于用户操作。

建议先交付一个受信任的合成包和一个真实高频应用包，验证无需终端的导入、确认、运行、停止与再启动，再推广格式。安装前检查 Python/Node 和指定依赖；不静默安装依赖，不自动执行未知代码。

### 2. 次日重建与旧实例辨认

当前没有完整单实例行为；重复启动可产生多个 Host，各有独立描述文件。多数窗口/租约/设置仍是内存状态；locale 和字号已有局部持久化，不能笼统说“什么都不保存”。

建议保存明确的本机 UI 偏好和可分享的无业务数据配方，重建时使用新 world/session/lease。保存窗口布局不等于永久绑定，也不要求把笔记、时间块或授权令牌存进 Host。代码启动仍逐次确认；凭据保存若另行实现，使用独立本机秘密存储设计。

### 3. 常驻窗口必须好读、少占地方

本次两个深色半透明窗口与后方文字叠加，明显干扰阅读。源码把 `surface_opacity` 应用于整个 frame，文字也参与透明。字号已有键盘入口，Alt+滚轮透明度入口未实现。

建议先区分背景透明度与文字对比度，并补用户能找到的外观设置。保留已决定的 0.8 默认，提供清晰的本机覆盖；阅读/输入型窗口可采用更不透明预设。默认总览压缩为少量摘要，来源与详情按需披露。宽度、折叠、临时隐藏和找回遵循同一套规则。

### 4. 信息必须能解释自己的确定程度

进程在线、读取成功、文件事件时间、逐会话运行状态是四个问题。本次 Claude 离线历史的 128 条有界记录仍显示为“后台 Agent”；该值不是 128 个正在工作的 Agent，也不是完整历史总量。App 页的 `0 running` 与 `128 unknown` 并列，仍容易被看成“确认没有运行任务”。

建议分别显示“应用进程”“最近读取”“来源更新”“会话状态”，把有界历史标成“已读取最多 N 条历史”。未查询的来源从主总览收起，不显示为空。当前线程最近输出缺失要显示边界并定位适配差异；不读取 thinking/完整对话来凑齐输出，不猜逐会话活跃数。

### 5. 可信地回到源应用

受限 Obsidian/TrafficMonitor 原生动作、UUID-only Codex 导航和 Provider 动作回执已有基础，但实际聚焦、目标歧义和拒绝前台激活仍需要原生验收。观察会话不等于拥有批准权限。先完成“看到 → 点击 → 到正确来源”的单步闭环，再扩展业务控制。

### 6. 真实工作日的故障恢复

已有 5/15/30 分钟刷新和若干崩溃探针，仍缺少当前构建跨工作时段的启动/退出/睡眠唤醒、多屏、穿透救援和孤儿进程检查。全虚拟桌面显示是独立平台缺口，不能用置顶替代，也不能提供空开关。

## 建议的下一阶段执行顺序

以下是本次审计建议，不是已完成或已排期的承诺。

| 顺序 | 可交付结果 | 可观察的完成条件 |
|---|---|---|
| A：可启动 | 当前构建 + 应用库 + 一个真实应用包 | 普通用户用文件选择/拖入和确认完成启动；不复制 descriptor、不打开终端；缺依赖有明确说明 |
| B：可信可读 | Agent 总览语义和常驻外观 | 离线历史不冒充活跃；读取/来源时间分开；本项目卡片有合法输出或明确原因；文字不与背景混淆 |
| C：可恢复 | 单实例与恢复工作台入口 | 重复双击聚焦同一个管理器；重启后列出已安装应用；确认后创建新世界/租约并恢复用户偏好 |
| D：有实际价值 | 先选 Agent 总览、TrafficMonitor、额度中的一至两个，再接通用 Obsidian | 每个应用从安装到停止独立验收；来源断开后状态诚实；点击回到正确来源 |
| E：日用候选 | 受控的数个真实工作时段 | 启动/显隐/折叠/恢复/退出可复现；休眠、断线和一次故障后可找回；记录资源与失败，修复后复验 |

建议把“首次配置后可独立使用”“每次启动无需命令行”“发生故障时用户知道下一步”作为本阶段发布门。三个目标全部可用实测判定，不用估算完成百分比。

Android、SysTorch、TouchAI、语音、桌面分身和 macOS 暂不阻挡上述 Windows 日用闭环；只有当选定日常场景确实依赖它们时才提升优先级。

## 本轮推进（2026-11-01）

Agent Activity 已加入世界管理器的双语控制卡，可一键启动、停止和重启；停止先让 Provider 清理临时世界。总览的读取条数现标为历史记录，活跃数只统计权威已知状态；来源最近读取时间与 SQLite/会话文件更新时间分开显示，每个来源页也列出逐会话记录更新时间。Codex App 输出只有在 rollout `session_meta` UUID 匹配后才会展示。

当前 EXE 为 14,402,560 bytes，SHA-256 `A2642924DC770A1B8B6C6E92921D42399A97C5D80379C98F8BEEE9D8F5EA40AB`。manager 使用 `--open-manager` 启动并被本机窗口枚举发现；Computer Use 两次激活新窗口都失败，因此没有完成原生按钮和卡片点击验收。Agent Activity 生命周期经 Windows 子进程测试和真实 release headless Host smoke 验证。示例 Provider 源码仍在核心 checkout，独立 `wincraft-agent-activity` 包尚未交付。

## 参照与方法

- 从 Rainmeter 学习包与安装入口：其正常安装通过文件关联把双击 `.rmskin` 接到安装对话框。由此建议 WinCraft 把用户入口从仓库脚本提升到受检包；不引入其插件执行模型。[官方安装文档](https://docs.rainmeter.net/manual/installing-skins/)
- 从 PowerToys Workspaces 学习“恢复一个工作场景”及逐应用启动结果，而不是让用户重新安排一切。这是体验参考，WinCraft 仍重新协商权限、创建窗口并确认代码执行。[微软文档](https://learn.microsoft.com/en-us/windows/powertoys/workspaces)
- 全虚拟桌面显示需单独验证平台适配；Tauri `set_visible_on_all_workspaces` 官方文档将 Windows 标为 unsupported。[Tauri Window](https://docs.rs/tauri/latest/tauri/window/struct.Window.html#method.set_visible_on_all_workspaces)
- 调查沿“用户意图 → 当前实现 → 本机行为 → 反例 → 验收 → 最小修订”推进；把计划资产、合成测试、真实协议、原生 UI 和持续日用分别记录。静态数量与 CI 不能替代用户旅程。
